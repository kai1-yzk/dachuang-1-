# 轻量化智能运维防护平台作品说明书（章节草案）

## 第1章 作品概述

本作品来源于团队在中小规模服务器集群运维中的真实痛点：工具分散、人工巡检滞后、高危命令缺乏约束、故障复盘证据不完整。基于此，我们设计并实现了“轻量化智能运维防护平台”，以“可观测、可执行、可审计、可扩展”为核心目标，将监控、服务管理、终端运维、文件管理、备份恢复、批量命令审批、AI 预测分析整合到统一控制台。

作品主要面向三类用户：

1. 中小企业运维工程师与值班人员。
2. 需要多服务器统一纳管的开发团队。
3. 关注运维合规与安全审计的管理人员。

作品主要功能与特色包括：

1. 多服务器接入与统一运维入口（SSH 纳管）。
2. 实时指标采集与大屏可视化（CPU、内存、磁盘、网络）。
3. 常见服务管理（启动、停止、重启、自启动切换）。
4. AI 异常预测与解释（异常评分、故障类型、处置建议）。
5. 高风险命令拦截与审批确认机制。
6. 全链路审计日志，实现“谁在何时对哪台机器做了什么”的可追溯。

应用价值体现在三方面：

1. 提升效率：将多系统操作聚合为单平台流程。
2. 降低风险：通过命令风控、角色权限和审计留痕降低误操作风险。
3. 支撑决策：通过历史数据、趋势分析和风险告警辅助运维决策。

推广前景方面，本作品具备“低门槛部署、模块化扩展、场景适配强”的特点，适用于高校实验室、创业团队、政企中小规模业务系统，也可进一步扩展为多集群、多租户、跨云环境的运维中台。

## 第2章 问题分析

### 2.1 问题来源

随着业务系统从单机向多节点扩展，传统运维方式暴露出明显短板：

1. 数据分散：监控、日志、命令执行分布在不同工具，信息孤岛明显。
2. 响应滞后：异常发现依赖人工巡检，故障定位时间长。
3. 风险不可控：命令直接执行缺乏分级拦截和审批机制。
4. 审计不足：关键操作过程记录不完整，难以复盘和追责。

### 2.2 现有解决方案

当前常见方案主要包括：

1. 传统监控栈（如 Prometheus + Grafana）：观测能力强，但执行闭环与审批审计需要额外系统拼接。
2. 运维面板工具（如部分服务器面板）：操作便捷，但在多租户、批量审批、AI 分析方面通常较弱。
3. 企业级 AIOps 产品：能力全面，但部署和维护成本较高，不利于中小团队落地。

| 部署成本 | 中           | 低         | 低-中  |

### 2.3 本作品要解决的痛点问题

基于对比，本作品聚焦解决以下核心痛点：

1. 监控与执行割裂：实现“发现问题-执行处置-结果追踪”的统一闭环。
2. 高危操作不可控：对命令执行进行风险评估、权限校验与必要确认。
3. 多服务器运维效率低：支持统一纳管、批量任务与状态可视化。
4. 复盘困难：关键操作写入审计日志，支持故障事件回放。

### 2.4 解决问题的思路

本作品采用“数据驱动 + 风险约束 + 模型辅助”的设计思路：

1. 功能需求：

- 支持多服务器接入、服务管理、文件管理、备份恢复、批量命令、终端交互。
- 支持异常预测接口与可解释输出。
- 支持按角色的访问控制和审计记录。

1. 性能需求：

- 常规查询接口秒级响应。
- 关键控制接口具备明确错误码与可诊断信息。
- 支持异步任务处理，避免阻塞主请求线程。

1. 数据集与数据来源：

- 公开数据：UNSW-NB15（网络入侵场景）、GAIA 智能运维数据集（日志/指标场景）。
- 平台数据：受管服务器实时采集指标（CPU、内存、磁盘、网络）。

1. 数据格式与特点：

- 时序数据：按时间戳组织的指标序列（JSON/表结构）。
- 日志数据：半结构化文本，需清洗与特征提取。
- 数据规模：支持从小规模（单机）到多机并发采集扩展。

## 第3章 技术方案

本章从原理层面介绍系统方案。整体采用前后端分离与异步任务架构，构建“采集-预处理-分析-执行-审计”闭环。

### 3.1 总体方案与技术路线

系统总体由六部分组成：

1. 数据采集层：通过 SSH 采集服务器实时指标。
2. 接口服务层：Flask 蓝图化 API 对外提供能力。
3. 分析决策层：融合规则与模型进行异常识别和风险评估。
4. 执行控制层：服务控制、终端命令、批量任务下发。
5. 安全审计层：RBAC 权限、风控策略、审计日志。
6. 展示交互层：Vue 控制台与可视化页面。

图 3 技术路线框架图（建议插入架构图：docs/architecture_8_layers.mmd）

### 3.2 关键模块技术原理

1. 监控与趋势模块：

- 使用时序数据聚合展示当前负载与历史趋势。
- 提供按时间窗口查询与趋势绘制。

1. 异常检测模块：

- 模型层采用轻量时序分析与异常检测思路。
- 工程上采用“模型优先 + 规则降级”策略，保证接口稳定性。

1. 风险控制模块：

- 命令白名单/黑名单与关键字拦截。
- 角色权限校验，防止越权操作。

1. 审计模块：

- 对关键动作记录操作主体、时间、对象、结果。
- 支持后续安全追踪与责任界定。

### 3.3 模型、算法与协议

1. 模型与算法：

- 时序预测思想：LSTM 类方法用于趋势建模。
- 异常检测思想：Isolation Forest 类方法用于离群识别。
- 风险评估：规则引擎与风险评分融合。

1. 协议与通信：

- REST API 用于业务请求。
- WebSocket 用于终端实时交互。

1. 数据存储与队列：

- MySQL 负责持久化。
- Redis + Celery 支持异步任务执行。

### 3.4 原创与增量工作说明

1. 原创性工作：

- 面向中小运维团队的“轻量一体化闭环”落地方案。
- 将命令风险评估、审批确认、审计留痕与运维执行深度结合。

1. 增量工作：

- 在通用监控与运维能力基础上引入 AI 预测解释层。
- 增强服务存在性检查与错误语义化返回，提高可运维性。

## 第4章 系统实现

### 4.1 软件架构与模块实现

系统由前端、后端、任务队列、数据库组成：

1. 前端：Vue 3 + Vite + Element Plus，负责操作入口与可视化。
2. 后端：Flask 蓝图化组织各业务域接口。
3. 异步任务：Celery Worker 处理耗时任务。
4. 存储：MySQL 保存用户、服务器、指标、审计等数据。

### 4.2 用户界面实现

1. 监控大屏：展示资源指标、趋势与风险状态。
2. 服务管理页：提供服务启停、自启动管理与状态查看。
3. 文件管理页：支持远程文件浏览、编辑、删除等操作。
4. 终端页：支持实时命令交互与回显。

图 4 系统主要页面示意（监控大屏、服务管理、终端）

### 4.3 数据来源与训练实现

1. 数据来源：

- 公开数据集用于模型开发验证。
- 真实服务器指标用于在线分析与展示。

1. 训练与推理：

- 训练脚本位于 AI 引擎模块。
- 推理接口在后端统一封装，支持降级策略。

### 4.4 部署方法

支持两种部署方式：

1. 本地开发部署：前后端分开启动，便于调试。
2. 容器化部署：通过 Docker Compose 一键编排。

### 4.5 开发难点与解决方案

1. 难点：模型不可用时接口不稳定。

- 解决：引入规则降级，保障核心页面可用。

1. 难点：服务控制在不同系统差异较大。

- 解决：增加多命令兼容回退策略。

1. 难点：权限与操作灵活性平衡。

- 解决：按角色分级授权并保留敏感操作更高权限门槛。

## 第5章 测试分析

本章通过功能、稳定性和安全性测试验证系统有效性。第2章提出的关键指标在本章对应印证。

### 5.1 测试数据来源与规模

1. 功能测试数据：来自本系统 API 调用与页面操作链路。
2. 指标测试数据：来自受管服务器实时采集样本与历史记录。
3. AI 相关测试数据：公开数据集样本与平台真实指标样本。

### 5.2 测试过程

1. 接口功能测试：

- 覆盖认证、服务器接入、服务控制、文件管理、预测接口。

1. 稳定性测试：

- 验证模型缺失/异常情况下预测接口是否可降级返回。
- 验证异步任务链路在常见异常下的可恢复性。

1. 权限与安全测试：

- 验证角色边界（普通运维、租户管理员、平台管理员）。
- 验证高危命令拦截与审计记录是否生效。

## 第6章 作品总结

本作品完成了从需求分析、技术设计、系统实现到测试验证的完整流程，实现了面向真实运维场景的轻量化平台。

### 6.1 作品特色与创新点

1. 一体化：监控、执行、审计融合在同一平台。
2. 轻量化：部署成本可控，适配中小团队。
3. 风险可控：命令风控 + 权限校验 + 审计闭环。
4. 可进化：支持规则与模型协同，便于持续优化。

### 6.2 应用推广

1. 校园实验室与教学实训平台。
2. 初创企业业务运维平台。
3. 区域政企部门的小规模 IT 运维场景。

### 6.3 作品展望

1. 引入更完善的模型评估体系和在线反馈学习机制。
2. 扩展多集群、多云和跨地域纳管能力。
3. 增强自动化处置编排，实现更高等级的自治运维。
