# 项目后续功能开发建议（详细版）

## 1. 背景与目标

当前项目已经具备以下能力：
- 多服务器接入（SSH/Agent）
- 指标采集与监控大屏展示
- AI 终端命令风控与审计
- 基础异常预测能力（基于 `server_metrics`）

下一阶段建议从“可运营、可闭环、可规模化”三个维度继续演进，目标是把系统从“可用 Demo”升级为“可落地的智能运维平台”。

## 2. 研发优先级原则

建议按以下原则排序：
- 先做高价值闭环：能直接降低故障时长（MTTR）和误报率
- 再做平台能力：多租户、权限、可观测性、可靠性
- 最后做增强体验：可解释 AI、自动化编排、知识化助手

优先级定义：
- P0：1-2 个迭代必须做，直接影响可用性与上线质量
- P1：3-5 个迭代重点做，显著提升竞争力
- P2：中长期能力，形成护城河

## 3. 功能路线（按价值分层）

## 3.1 P0 功能（强烈建议优先）

### P0-1 告警中心与通知编排
- 目标：将异常预测结果变成可行动告警，避免只在页面展示。
- 用户价值：值班人员可第一时间收到告警，缩短响应时间。
- 建议实现：
  - 新增 `alerts` 表（状态、级别、来源、去重键、首次/最近触发时间）。
  - 将 `/api/ai/predict/server/{id}` 的输出接入告警生成逻辑。
  - 支持通知渠道：邮件、企业微信/钉钉 Webhook。
  - 告警去重与抑制：同一服务器同一指标在窗口内只触发一次。
- 验收指标：
  - 重复告警降低 50%+
  - 告警触达延迟 < 10s

### P0-2 事件工单闭环（Ack/指派/恢复）
- 目标：从“检测”升级到“处置流程”。
- 用户价值：告警有人负责、有处理记录、有恢复确认。
- 建议实现：
  - 新增 `incidents` 表，状态流转：`open -> acknowledged -> resolving -> resolved -> closed`。
  - 前端新增“事件中心”页面，支持认领、转派、备注、关闭。
  - 与审计日志打通，形成完整追溯链。
- 验收指标：
  - 事件闭环率 >= 90%
  - 平均确认时长（MTTA）可量化

### P0-3 模型在线校准与阈值管理
- 目标：降低当前模型误报，支持按服务器差异化阈值。
- 用户价值：告警更准确，不打扰业务。
- 建议实现：
  - 新增 `model_thresholds` 配置表（按服务器/指标/时间段）。
  - 记录每次预测输出，支持回放与离线评估。
  - 提供“误报/漏报”反馈按钮，形成再训练样本。
- 验收指标：
  - 精确率提升 30%+
  - 误报率持续下降

### P0-4 采集链路稳定性增强
- 目标：保障数据连续可用，避免大屏与模型断流。
- 用户价值：监控可信，不因偶发网络抖动丢失关键指标。
- 建议实现：
  - 采集任务异步化（Celery Beat 周期采集），失败重试与退避。
  - 为 `server_metrics` 增加采集状态字段与失败原因记录。
  - 后端增加 `/api/metrics/collector/status` 健康接口。
- 验收指标：
  - 指标缺失率 < 1%
  - 采集失败可观测、可定位

## 3.2 P1 功能（明显提升平台能力）

### P1-1 自动化运维剧本（Runbook）
- 目标：把常见故障处置从人工命令转为自动化流程。
- 用户价值：标准化处理，降低人为失误。
- 建议实现：
  - 新增 `runbooks`（YAML/JSON 步骤定义）。
  - 支持触发方式：手动触发、告警自动触发（需审批）。
  - 执行记录写入审计，支持回滚动作。
- 典型场景：磁盘爆满清理、服务重启、连接数异常处理。

### P1-2 智能根因分析（RCA）
- 目标：从“发现异常”升级到“解释异常”。
- 用户价值：减少排查时间，提升定位效率。
- 建议实现：
  - 融合指标、日志、命令审计三类证据。
  - 建立“异常前后 15 分钟”的特征切片。
  - 输出 Top-K 根因候选及置信度。
- 验收指标：
  - 故障定位平均时长下降 20%+

### P1-3 多租户与资源隔离
- 目标：支持不同团队/客户共用平台。
- 用户价值：平台可对外服务化，支撑规模扩展。
- 建议实现：
  - 关键表增加 `tenant_id`。
  - RBAC 升级为租户级权限控制。
  - 接口默认按租户过滤并做权限校验。

### P1-4 凭据与密钥管理中心
- 目标：替代明文凭据存储，降低安全风险。
- 用户价值：满足生产安全要求。
- 建议实现：
  - 对 SSH 密码/密钥进行加密存储（建议 KMS 或至少 AES + 密钥轮换）。
  - 凭据操作全审计（谁在何时修改了什么）。
  - 强制密钥脱敏显示。

## 3.3 P2 功能（中长期护城河）

### P2-1 数字运维助手（知识问答 + 操作建议）
- 目标：让值班人员通过自然语言快速获取诊断和操作建议。
- 用户价值：降低门槛，提升处理速度。
- 建议实现：
  - 接入知识库（历史告警、工单、Runbook）。
  - RAG 检索后输出可执行建议。
  - 高危建议必须走审批链。

### P2-2 变更风险评估
- 目标：在变更前预测故障概率，减少发布事故。
- 用户价值：发布更稳，回滚更少。
- 建议实现：
  - 输入变更类型、历史同类记录、当前系统健康度。
  - 输出风险分与保护建议（灰度比例、观察窗口）。

### P2-3 容量预测与成本优化
- 目标：提前发现资源瓶颈，优化资源使用成本。
- 用户价值：避免“突发扩容”与资源浪费。
- 建议实现：
  - 周/日粒度趋势预测。
  - 提供容量建议与节省估算。

## 4. 数据与模型建设建议

- 建立训练数据分层：
  - `raw`：原始采集数据
  - `feature`：特征快照
  - `label`：人工标注与反馈标签
- 建立评估看板：
  - 指标：Precision、Recall、F1、误报率、漏报率、告警提前量
- 训练流程标准化：
  - 周期训练（如每周）
  - 灰度发布（新旧模型并行对比）
  - 线上回滚机制

## 5. 建议的数据表增量（示意）

建议新增：
- `alerts`
- `incidents`
- `model_predictions`
- `model_thresholds`
- `runbooks`
- `credential_events`

建议扩展：
- `server_metrics` 增加 `collector_status`、`collector_error`
- `audit_logs` 增加 `trace_id`、`incident_id`

## 6. 12 周实施节奏建议

### 第 1-4 周（P0）
- 告警中心 + 通知
- 事件闭环
- 阈值管理
- 采集链路稳定性

### 第 5-8 周（P1）
- Runbook 自动化
- 根因分析 MVP
- 多租户基础
- 凭据管理加固

### 第 9-12 周（P2 预研 + 部分上线）
- 知识助手 MVP
- 容量预测 MVP
- 变更风险评估方案设计

## 7. 近期最值得做的 3 个功能（结论）

如果你希望短期内“看得见效果”，优先开发：
- 告警中心与通知编排（让异常能被看见）
- 事件工单闭环（让异常有人处理）
- 在线阈值校准（让异常更准确）

这三项完成后，平台会从“监控展示系统”升级为“可运营的智能运维系统”。
